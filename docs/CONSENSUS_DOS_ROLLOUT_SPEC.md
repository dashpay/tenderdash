# Consensus DoS — rollout spec (devnet → testnet)

Status: draft for review. Covers validating the Phase-1 defences on a controlled network,
then a wider one, and the observability needed to tell "the throttle is working" from "the
throttle is starving us". Phase-1 implementation is complete (60 commits, see
`docs/CONSENSUS_DOS_PLAN.md`); nothing here changes the defences themselves.

## 0. The one question this rollout must answer

Every Phase-1 defence sheds load. The measured in-process results say honest traffic survives,
but **the load suite injects messages *below* the reactor** — downstream of the per-peer channel
limiters, protobuf conversion and structural validation. So the layer that actually does the
rejecting has never been exercised against realistic traffic.

> **Is the node shedding attack traffic, or is it shedding honest traffic?**

Everything below exists to answer that with evidence, on a real network, before mainnet.

## 1. Blockers — fix before any node is deployed

These are operator-facing defects found during rollout planning. They are cheap and they will
bite silently.

- **B1 (breaks startup).** `verification-rate-limit` set anywhere in `(0, 33)` now fails
  `ValidateBasic` — the node **will not start**. `MinVerificationRateLimit = 33`. Any operator
  who previously tuned this down is broken by the upgrade. Must be in release notes and
  `UPGRADING.md`.
- **B2 (silent vote loss).** `peer-vote-rate-limit` changed default 100 → 600 **and changed
  units** from *messages* to *verification work*. An operator whose existing `config.toml`
  carries `100` keeps the number and silently gets ~10 realistic precommits/s per peer. This is
  the single most likely cause of an observable regression in the field.
- ~~**B3 (ships wrong guidance).**~~ **DONE** (`4c21acddb`). The generated template now renders
  both figures from `MinVerificationRateLimit` via a template FuncMap, so it cannot drift from
  the runtime constant again. A fourth stale `66` in `internal/consensus/reactor.go` was found
  and fixed at the same time.
- **B4.** `docs/nodes/metrics.md` documents none of the new metrics, and
  `consensus_vote_gate_fail_open` was **removed**. Nothing checked in anywhere in the org
  references it (§1a), so this is a docs gap rather than a breakage.
- **B5.** `UPGRADING.md` has no Tenderdash 1.x section at all (latest is upstream v0.36). B1/B2
  belong there.

## 1a. What already exists in the dashpay org (surveyed — reuse this)

**Deployment: fully reusable, one knob.** `dashpay/dash-network-deploy` (Terraform on AWS +
Ansible, services via Docker Compose; validators managed by dashmate) has a turnkey
`.github/workflows/create-devnet.yml` (`workflow_dispatch`: devnet name, node counts, versions),
with `destroy-devnet.yml` alongside. Config sets live in `dashpay/dash-network-configs`
(`<network>.{yml,tfvars,inventory}`), and devnet sets live on branches. Re-running with an
existing set enters resume mode and skips Terraform.

**Pointing it at our build is a single variable:** `tendermint_image` in the network yml (default
`dashpay/tenderdash`, testnet pins `dashpay/tenderdash:1.6.0`). It covers **both** paths — seed
nodes via `roles/tenderdash/templates/docker-compose.yml.j2` and the actual validators via
`roles/dashmate/templates/dashmate.json.j2`. Caveat: `create-devnet.yml` sed-patches only the
platform/core images, **not** `tendermint_image` — so either pre-seed the config set (resume
path), add a sed step/input, or deploy manually with `./bin/deploy`. Pre-release images on
devnets are routine practice here.

**Config plumbing gap — blocks tuning.** Tenderdash's `config.toml` is generated by dashmate, so
knobs must be plumbed: `<network>.yml` → ansible vars (`roles/dashmate/defaults/main.yml`) →
`dashmate.json.j2` → dashmate's own template in `dashpay/platform`
(`packages/dashmate/templates/platform/drive/tenderdash/config.toml.dot`). Only a partial
`[consensus]`/`[p2p]`/`[mempool]` surface is exposed today, and **none of the DoS knobs
(`verification-rate-limit`, `peer-vote-rate-limit`, `peer-data-rate-limit`) are plumbed at all**.
Consequences:
- A devnet runs whatever Tenderdash's *defaults* are; we cannot sweep the limits per-network
  without a **cross-repo change** (platform → dash-network-deploy → dash-network-configs).
- Conversely, because dashmate regenerates `config.toml`, the B2 unit trap does **not** hit
  dashmate-managed nodes — they get the new defaults. **B2 hits hand-rolled configs only**
  (seed nodes, bespoke operators). That narrows the release-note audience but does not remove it.
- Several Phase-1 constants are sized against `MaxConnections + 4 = 68`, and `max_connections`
  **is** plumbed — so a devnet overriding it silently mis-sizes them (see §7).

**Observability: scraping reusable, visualisation is greenfield.** `roles/metrics/` ships
haproxy + prometheus + grafana on a dedicated host. Scrape jobs cover `tenderdash` on all
**HP masternodes at :36660** — **seed nodes are not scraped** even though their template enables
prometheus. Namespace is `drive_tenderdash`, so our metrics appear as
`drive_tenderdash_consensus_*`, not `tendermint_*`. Alerting is **two rules**
(`roles/metrics/files/prometheus/rules.yml`): `ChainHalt` (block height rate == 0 for 10m) and
`RoundTooHigh` (rounds > 3 for 1m) — and `alertmanagers` is empty, so nothing is actually
delivered. **No grafana dashboard JSON exists anywhere in the org**; dashboards are hand-built
and live only on the metrics host's disk. Good news: nothing checked in references the metric we
removed, so removing `consensus_vote_gate_fail_open` breaks no committed config. Check the live
testnet metrics box for a hand-built dashboard before assuming none exists.

**Stress tooling: nothing reusable — confirmed.** There is **no p2p/consensus-level load or
attack tool anywhere in the dashpay org.** Everything found is transaction/state-transition
level and would not touch the verification budget, the lanes, or the per-peer limiters:
- `roles/load_tool` provisions load hosts and clones `platform-tui@load-test`
  (`src/bin/load-test.rs`, `--connections/--time/--rate`) — broadcasts **state transitions via
  DAPI**. Last commit Feb 2024, pinned to `PlatformVersion::get(1)`; ~2 years stale and unlikely
  to build.
- `platform/packages/bench-suite`, `strategy-tests` — application level, and strategy tests run
  in-process against ABCI with no real network.
- Tenderdash `test/e2e/runner`: `load.go` is tx-level; `perturb.go` does node kill/pause/restart
  only; the upstream byzantine/maverick node implementation is **gone** (only a stray
  `entrypoint-maverick` remains).
No trace of the mid-2025 stress test exists in any repo — it was most likely run ad hoc with the
2024 `load_tool`. **Ask the operator who ran it what was actually exercised before assuming it
covered consensus messages.**

⇒ §3's flood client must be built. It is the single largest piece of new work in this rollout,
and without it the devnet phase cannot answer §0.

## 2. Images and the embargo

`docker.yml` publishes to **public Docker Hub** (`dashpay/tenderdash`) on `release: published`
or `workflow_dispatch` with a custom tag. There is **no private registry** in the pipeline, so
"private images" is not currently satisfiable by the shipped workflow.

**DECIDED: public image is acceptable.** The operator has accepted publishing to public Docker
Hub (`dashpay/tenderdash:<tag>`), which is what the shipped `docker.yml` `workflow_dispatch`
already does and what `tendermint_image` expects. The options below are retained only as a record
of what was weighed; disclosure timing is no longer treated as a blocker for this rollout.

Options, in order of embargo strength:
- **(a) Self-hosted / local only.** Build with `make build-docker` and load onto operator-run
  hosts, or push to a registry inside the operator's own network. Strongest; no third party ever
  holds the artefact. Adequate for devnet.
- **(b) GHCR private package on the private fork.** Add a workflow publishing to
  `ghcr.io/<private-fork>/tenderdash`, inheriting the repository's private visibility, with
  pull access granted per-operator. Needed if testnet nodes are run by anyone but us.
- **(c) Obscure tag on public Docker Hub.** What the current pipeline offers. **Not an embargo
  control** — public registries are enumerable and pullable.

**Disclosure timing is a release-management decision, not a technical one.** Any binary carrying
these defences can be diffed against public v1.6 to locate the vulnerability while mainnet is
unpatched. Recommendation: **operator-run nodes only for §5 (adversarial devnet)**; community
participation only once mainnet's upgrade is scheduled. Record the decision here before §6.

Build metadata is already useful: a branch build embeds `unreleased-<branch>-<full sha>` in the
version string, so `/status` identifies exactly what a node is running. Use branch builds for
devnet rather than tagged releases.

## 3. Missing tooling: a network-level flood client (required for §5)

**There is no tool in this repo that floods consensus messages at a running network.** Tx load
(`runner load`) and evidence injection (`runner evidence`) exist; neither exercises the
verification budget, the lanes, the per-peer limiters or the channel ceilings.

Build a minimal p2p-level flood client. Requirements:
- Speaks the real p2p handshake as an ordinary peer (many identities — node IDs are free, which
  is the threat model), connects to a target node, and sends on the consensus channels.
- Message profiles, each independently selectable, matching the measured attack shapes:
  1. **prevote, forged block signature** — the cheap flood (costs the victim 1 work unit;
     highest message rate per slot at ~600/s);
  2. **precommit declaring 32 extensions, forged block signature** — proves staged permits
     charge 1, not 33;
  3. **valid block signature, invalid final extension**;
  4. **forged commit** (ungated, unattributable);
  5. **forged proposal** (~100/s per slot; now budget-charged);
  6. **repeated identical and mutated near-64 KB invalid BlockPart proofs**;
  7. **State/VoteSetBits at max connections incl. 10k-bit arrays**; duplicate and novel
     `VoteSetMaj23`;
  8. **evidence flood with byte-flipped signatures** (defeats hash dedup, not identity dedup).
- Controls: identities, per-identity rate, duration, ramp; and a **mixed** mode running an
  honest client alongside so honest service is measured under the same run.
- It must be able to saturate: the design point is 68 connection slots, so it needs to hold most
  of them.

Keep it out of the production build (separate `test/` tool or build tag). It is an attack tool
for a private fork under embargo — do not publish it with the fix.

## 4. Observability (build before §5; it *is* the experiment's instrument)

`[instrumentation] prometheus` defaults to **false** — enable it on every devnet/testnet node,
and raise `max-open-connections` (default 3) if scraping from more than one place.

**Metrics that exist now** — consensus: `peer_lane_drops`, `block_part_proof_drops`,
`state_channel_drops`, `proposal_verify_failures`, `verification_budget_drops`; evidence:
`dropped_evidence{reason}` with `structural|oversized|already_known|height_window|node_budget|peer_budget`.

**Gaps to close before the experiment.** The existing counters say *that* we dropped, not
*whether we should have*:
- **Per-peer attribution** on the consensus drop counters (at minimum honest-vs-flood
  separable). Without it, "1M drops" is unreadable. Mind cardinality — a label per node ID is
  not viable at 68 peers × several counters; prefer a small bounded classification.
- **Honest-vote latency** — receipt→counted, as a histogram. This is *the* number: the fair-share
  bound predicts ~4.5 s at 100 validators under flood versus a 1 s vote timeout.
- **Budget saturation** — a gauge of how full the verification budget is, and time spent waiting.
- **Lane depth / rotation size** — to see fairness working and to catch identity-rotation lane
  growth.
- Reason labels on consensus drops, matching the evidence gate's `reason` convention.

**Dashboards and alerts are greenfield** — nothing exists in-repo. Build one dashboard that
answers §0 at a glance: block time and round count on top; drop rates by reason and honest-vote
latency beneath; budget saturation and lane depth below that. Alert on *honest* symptoms —
rising round count, honest-vote latency above the vote timeout, block time regression — **not**
on drop counters, which are supposed to rise under attack.

**Logging.** Many peer-triggerable rejections were deliberately moved to Debug to stop
log-amplification, so at `info` the counters are the only signal. Run devnet consensus/evidence
modules at debug; do **not** do that on testnet under flood (that is the amplification the fix
exists to prevent).

## 5. Devnet — controlled and adversarial

Operator-run only. Use the e2e harness for the network (`runner setup` / `start`, and simply do
not `cleanup`; `pause`/`resume`/`load`/`evidence`/`tail` all work against a live network), or
`networks/remote/` terraform+ansible for multi-host (upstream-inherited, likely stale — budget
time to repair or replace).

Baseline first: same network, same load, on the **merge-base** build. Every number below is a
comparison, not an absolute.

| # | Scenario | Pass criteria |
|---|---|---|
| D1 | Clean network, no attacker, ≥24 h soak | Block time and round distribution within noise of baseline. Zero unexplained drops. |
| D2 | Each flood profile (§3) individually, at saturation | Chain keeps committing. Honest-vote latency below `timeout_propose`. Drops attributable to the flood. Zero peer evictions. |
| D3 | All profiles combined, all slots held | Same, and the node recovers to D1 behaviour within one height of the flood stopping. |
| D4 | **Honest catch-up under flood** — restart a validator and let it resync while flooded | It catches up. This is where the B2 unit change bites; measure `peer_lane_drops` and honest-vote latency for the catching-up peer specifically. |
| D5 | **Mixed version** — half old, half new, both directions | No stall, no fork, no partition. Watch the peer graph (§7). |
| D6 | Validator slot pressure — flood all inbound slots, then restart a validator | The validator reconnects and keeps its slot (this is what piece 3b bought: 0 → ≥18/68). |
| D7 | Config traps | A node with `verification-rate-limit = 10` fails to start with a clear message; a node left at `peer-vote-rate-limit = 100` shows the predicted vote loss (proves B2 is real and the release note is warranted). |
| D8 | Evidence — genuine equivocation **during** an evidence flood | The genuine evidence is still accepted and makes it into a block. This is the safety property, not a throughput one. |

**Exit criteria:** D1–D8 pass; every drop counter observed is explained; the dashboard answers
§0 without needing the raw logs.

## 6. Testnet — scale and reality

Only after §5 exits and the §2 disclosure decision is recorded.

- More nodes, real quorum size (the 100-validator figures so far are **arithmetic
  extrapolations** from a 24-validator fixture — linearity was measured, absolute numbers were
  not), real tx load, real rotation.
- Long soak across many quorum rotations, with vote extensions enabled — the single-verification
  predicate (`checkVoteClaim`, `AddVerifiedVote`) refuses rather than falls back, so an
  over-strict predicate is a halt risk that only accumulated rounds will surface.
- Repeat D2/D3/D4 at scale. Expect the fair-share bound (~4.5 s for a 100-validator precommit
  quorum under max flood) to become visible; confirm the measurement rather than assuming it.
- Community nodes last, per §2.

**Exit criteria:** a full rotation cycle under flood with no missed blocks attributable to the
defences; measured honest-vote latency and block time inside agreed thresholds; no operator
reports of vote loss traceable to B1/B2.

## 7. Known unknowns to resolve during rollout

- **Mixed-version peer graph.** `SetProtectedPeers` (new nodes reserve slots for the quorum, old
  nodes do not) and the DIP-6 ordering change in `6e6f72cb7` could make new and old nodes
  disagree about the overlay. It cannot fork the chain, but it can change who connects to whom.
  Needs a targeted review of that commit **and** D5 evidence.
- **Hardcoded constants sized against 68 peers.** `assumedMaxPeers`, `maj23NodeRateLimit`,
  `peerStateRateLimit`, evidence rates/bursts and the lane sizes are compile-time constants tuned
  for the default connection limits. A devnet/testnet running non-default `max-connections` will
  mis-size them, and the load suite's guard test only checks defaults. Either run defaults, or
  make the affected constants derive from config.
- **Real verifier throughput** — plan §9 still lists this as `[MEASURE]`. Devnet is where the
  per-platform number gets taken; the 300/s budget default depends on it.
- **Router inbound queue** is effectively unbounded and unobservable, and sits *upstream* of
  everything Phase 1 bounds. Add occupancy/drop metrics for it, or accept that §0 has a blind
  spot above the layer we instrumented.
